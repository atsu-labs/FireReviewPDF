# Issue対応ワークフロー・スキル

本スキルは、AIエージェントがGitHub Issueの対応を行うにあたり、要件の抜け漏れや認識の齟齬を防ぐため、事前に不明点・確認事項を洗い出して質問し、合意した内容をGitHub Issueへコメントとして整理・記録した上で開発に着手するための一連の手順を定義したものである。

## 0. 基本ルール（共通）

- **日本語の徹底**: ユーザーへの質問、Issueへのコメント、記録などはすべて**日本語**で記述する。
- **簡潔・明確な記述**: [development-rules.md](../../rules/development-rules.md) に準拠し、挨拶や定型句（「お世話になります」「ご確認ください」など）は省き、論点、確認事項、技術的な決定事項を端的に記述する。
- **合意形成の重視**: 不明点や仕様の曖昧さを残したまま実装を進めない。必ずユーザーとの合意を得てからIssueを整理し、開発へ進む。

---

## 1. Issue情報の取得と精査

Issueへの対応を開始する際は、まず対象Issueの最新情報を取得・分析する。

1. **Issue情報の取得**:
   - GitHub CLI (`gh`) を使用して、Issueのタイトル、本文、既存のやり取り（コメント群）を取得する。
   - コマンド例:
     ```bash
     gh issue view <Issue番号> --comments
     ```
2. **要件の精査と影響範囲の調査**:
   - 以下の観点でIssueの内容を精査する:
     - **目的・背景**: なぜこの変更・機能・修正が必要なのか
     - **期待される挙動**: 正常系・異常系、エッジケースの仕様が明示されているか
     - **既存システムへの影響**: 影響を受けるファイル、既存機能、UI/UX、データ構造
     - **受け入れ条件**: 何をもって完了とするかの基準があるか

---

## 2. 不明点・確認事項のヒアリング（質問と合意形成）

精査の結果に基づき、不明点や仕様の選択肢がある場合はユーザーへ確認を行う。

1. **確認事項の有無の判定**:
   - 以下のいずれかに該当する場合は、必ずユーザーに質問・確認を行う:
     - 仕様や要件に複数の解釈や実装方針が考えられる場合
     - エラーハンドリングや未考慮のエッジケースが存在する場合
     - UIデザインや文言、キーバインドなどのユーザー体験に関わる未確定要素がある場合
     - 既存のアーキテクチャやドキュメントとの整合性に疑問がある場合
2. **ユーザーへの質問・相談**:
   - 質問する際は、単に「どうしますか？」と聞くのではなく、**論点を整理し、具体的な選択肢や推奨案（理由付き）を提示**する。
   - 選択肢形式の質問には、状況に応じて `ask_question` ツールやMarkdownの箇条書きを活用する。
   - **質問例**:
     - 「〇〇の例外発生時の挙動について、以下のどちらの方針が望ましいでしょうか？
       1. (推奨) トースト通知を表示して処理を安全に中断する
       2. エラーダイアログを表示してリトライを促す」
3. **不明点がない場合**:
   - Issueの記述が十分に明確であり確認事項がない場合も、「以下の理解・方針で進めます」と要約を提示してユーザーに認識の確認を取る。

---

## 3. Issueへのコメント投稿と要件整理

ユーザーとの質問・回答を通じて方針や仕様が確定したら、その内容をIssueに記録・整理する。

1. **整理フォーマット**:
   Issueコメントには以下の構造を含める。

   ```markdown
   ## 対応方針と仕様整理

   ### 決定事項・要件の明確化
   - [ヒアリングや確認で合意・決定した仕様のポイント]
   - [スコープ外とする事項（あれば）]

   ### 実装方針
   - [変更対象モジュール・ファイル]
   - [設計・アプローチの概要]

   ### タスク一覧
   - [ ] [具体的な作業項目1]
   - [ ] [具体的な作業項目2]
   - [ ] 動作確認・テストの実施
   ```

2. **Issueへのコメント投稿**:
   - GitHub CLIを使用してコメントを投稿する。
   - コマンド例:
     ```bash
     gh issue comment <Issue番号> --body "## 対応方針と仕様整理..."
     ```
   - ※改行を含む長いテキストは、一時ファイルを作成して `--body-file` オプションで渡すか、適切にエスケープして実行する。
3. **CLIが利用できない場合の代替対応**:
   - `gh` コマンドがエラーまたは利用不可の場合は、コメント用の整理テキストをチャットで提示し、ユーザーにIssueへの投稿を依頼する。

---

## 4. 開発への接続（git-workflow連携）

Issueの整理・コメントが完了したら、実際の実装フェーズへと移行する。

1. **ユーザーへの報告**:
   - Issueへのコメントが完了したことを報告し、実装着手の準備が整ったことを伝える。
2. **ブランチ作成と開発着手**:
   - `git-workflow` スキルに従い、最新の `main` から作業ブランチを作成して実装を開始する。
   - ブランチ名例: `feat/issue-<番号>-<要約>` や `fix/issue-<番号>-<要約>`
   - プルリクエスト作成時には、対象Issueと紐付けるキーワード（`Closes #<番号>`）を含める。
